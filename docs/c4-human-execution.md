# C4 — Human acceptance execution package

Companion to `docs/c4-human-acceptance.md` (the authoritative 47-check
tracker: statuses, evidence, defect refs). This document is the
**tester's runbook** — what to install, what to prepare, and how to run
the five sessions. A check is PASS only after a human executes it and
records real evidence. Automated CDP results **never** substitute.

Record the build's commit hash on every check row you execute
(`Build` column in the tracker).

## Environment requirements

- Windows 10/11 x64 machine or VM you control (fresh profile preferred
  for W-series; a throwaway VM or Windows Sandbox is ideal).
- Headphones or speakers at a comfortable, consistent volume.
- Keyboard AND mouse available — but Session 5 forbids the mouse.
- ~2 GB free disk; no other heavy apps running during timing checks.
- Optional: NVDA (free, nvaccess.org) or built-in Narrator for K4.

## Setup (once, ~10 min)

1. Install the NSIS build, launch the app. First run shows the wizard.
2. Create a project (any name — e.g. `c4-accept`).
3. Seed the acceptance timelines: from a terminal in the repo
   (or ask engineering to run it against your installed app):

   ```
   node scripts\cdp-n3d-acceptance.cjs 9222 out\
   ```

   This creates the **FILM** timeline (dialogue + music + SFX, fades,
   automation, one crossfade) and **LONG** (high clip count) used by
   N3/L checks.
4. Synthetic media needed is generated by that seeding (speech-shaped
   test audio, tone music, SFX hits). No real TTS/cloud output exists
   or is required. If any check needs extra media, generate it in-app
   via the simulated pipeline or import a short WAV/MP4 you own.

## Status + evidence rules (Phase 4 rules)

- Statuses: **NOT RUN → PASS | FAIL | BLOCKED** only.
- Record on every executed row: tester name, date, build hash,
  evidence pointer, defect ref if failing.
- Evidence capture:
  - Screenshots: `Win+Shift+S` (Snipping Tool) — save beside the
    tracker as `docs/c4-evidence/human/<ID>-<desc>.png`.
  - Screen recording: `Win+Alt+R` (Game Bar) for timing/feel checks.
  - Listening: written observations are acceptable; note *what* you
    heard and *when* (e.g. "SFX 03 audibly late ~0.5s").
  - Exports: keep the output mp4 + note its path.
- Failing a check → file a defect (see below), put its ref in the
  `Defect ref` column, mark the check FAIL with evidence.
- Can't perform a check → **BLOCKED + reason**, never skipped silently.
- A fixed defect requires **retest** of the exact check row; update
  status only after real retest.

### Defect reporting

File as GitHub issue (or note in the tracker's section-6 register):

```
Check: <ID>   Build: <hash>   Severity: critical|high|medium|low
Steps: <numbered, minimal>   Expected / Actual: <one line each>
Evidence: <screenshot/log/audio note path>
```

Severity guide — *critical*: crash, data loss, security, wrong
project data; *high*: a required action unreachable or a wrong result
a tester would ship past; *medium*: degraded but workable; *low*:
cosmetic/nit.

## Session 1 — N3 audio/editing checklist (19 checks)

**Checks:** A1–A8, B1–B2, C1–C6, D1–D3
**Preconditions:** FILM + LONG timelines seeded; headphones on; app idle.
**Where:** procedures are authoritative in `docs/n3-human-checklist.md`
("How" + "Pass if" per item) — record results in
`c4-human-acceptance.md` section 1.
**Order:** run A-series (scrubbing) → B → C (editing feel) → D
(responsiveness on LONG). ~45–60 min.
**Tip:** these are *feel* checks — trust your ears/eyes, not the UI's
claims. "Feels immediate" is a judgment call; record hesitation as a
finding even if you pass the row.

## Session 2 — Listening tests (7 checks)

**Checks:** L1–L7 — procedures + expected results in
`c4-human-acceptance.md` section 2.
**Preconditions:** FILM timeline, headphones, quiet room.
**Note L2:** you must *confirm the app discloses simulation* — look for
the mock/simulated labeling, don't assume.
**Note L7:** export first, then watch the mp4 — sync judgments are
about the *rendered file*, not the preview.

## Session 3 — Usability tasks (7 checks)

**Checks:** U1–U7 — `c4-human-acceptance.md` section 3.
**Preconditions:** a genuinely first-time user if possible (not you if
you've used the app extensively); fresh project; no coaching —
the app must teach itself.
**Method:** observe quietly, note hesitation points verbatim. If no
novice is available, run self-test cold (clear mind, follow only
on-screen cues) and mark evidence "self-test" — downgrade confidence
and note it.

## Session 4 — Windows installation/interaction (9 checks)

**Checks:** W1–W9 — `c4-human-acceptance.md` section 4.
**Preconditions:** Windows machine/VM; ability to log off/on; a second
media player for W8.
**W4 (logoff):** start a simulated job first, then sign out/in.
**W9:** uninstall removes the app; check whether
`%LOCALAPPDATA%\AtomicAIStudio` data persists (record what you find —
data-dir behavior is the check).

## Session 5 — Keyboard/accessibility (5 checks)

**Checks:** K1–K5 — `c4-human-acceptance.md` section 5.
**Preconditions:** unplug/disable the mouse mentally — K1–K3 are
keyboard-only; K4 needs NVDA or Narrator.
**Reference keyboard model:** Tab between controls; on a focused clip
Enter/Space selects → inspector; ←/→ nudges 1 frame (Shift = ±1 s);
Ctrl+↑/↓ re-lanes; `s` splits at playhead; Delete removes; Ctrl+Z /
Ctrl+Shift+Z undo/redo; ruler is a slider (arrows/Home/End/PgUp/PgDn).
**K4:** NVDA (`Ctrl+Alt+N` to start Narrator if no NVDA) — listen to
what's actually announced, don't verify from the screen.

---

## After all sessions

1. Ensure every row is PASS/FAIL/BLOCKED with tester/date/build +
   evidence — no NOT RUN left unless explicitly BLOCKED.
2. Resolve all critical/high defects; retest those rows.
3. Document remaining medium/low in the defect register.
4. The C4 completion recommendation then goes to the owner —
   C4 closes only on explicit approval, never by inference.
